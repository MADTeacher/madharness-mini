# Лабораторные работы: 02-AGENTS-md

Эта ветка посвящена работе с проектными инструкциями `AGENTS.md`. Главный вопрос
главы: как harness добавляет к задаче пользователя устойчивые правила проекта из
корня рабочего пространства (workspace), показывает происхождение этих правил и
сохраняет ясные границы безопасности.

Базовая реализация намеренно проста: она читает только корневой `AGENTS.md`.
Глобальные пользовательские правила, вложенные `AGENTS.md`, семантика
переопределения и проверка инструкций для конкретного файла остаются
лабораторными расширениями.

## Базовый уровень

### 1. Добавить в трассу источник корневого `AGENTS.md`

Цель: сделать загрузку проектных инструкций наблюдаемой без раскрытия полного
текста правил в трассе.

Контекст проблемы: сейчас `load_project_instructions()` возвращает готовую
строку, а по трассе трудно понять, был ли корневой `AGENTS.md` найден, пропущен
как пустой или обрезан по лимиту.

Задание: добавьте событие трассы или поле в существующее событие запуска, которое
показывает путь к корневому `AGENTS.md`, статус загрузки (`used`, `missing`,
`empty`, `truncated`) и размер текста, добавленного в системный запрос.

Ограничения:

- не читать `AGENTS.md` за пределами `Config.root`;
- не писать полный текст инструкций в трассу;
- сохранить совместимость текущего системного запроса;
- не добавлять отдельный слой контекста из следующей ветки.

Критерий готовности: по трассе можно понять, какой корневой файл был учтён и
почему итоговый системный запрос получил именно такой объём инструкций.

Проверка: создайте временный проект с отсутствующим, пустым, обычным и слишком
большим корневым `AGENTS.md`; тесты должны проверить статусы без обращения к
модели.

### 2. Зафиксировать границу корневых инструкций

Цель: явно отделить базовую механику ветки от будущих расширений с вложенными
правилами.

Контекст проблемы: если harness запущен из подпапки, легко случайно начать
искать `AGENTS.md` по цепочке директорий. Для этой ветки такое поведение должно
быть осознанным расширением, а не скрытой частью базового контракта.

Задание: добавьте тесты и короткую диагностику, подтверждающие: harness
читает только `Config.root / "AGENTS.md"`, а `src/AGENTS.md` или
`services/payments/AGENTS.md` не попадают в стартовый системный запрос
автоматически.

Ограничения:

- не добавлять поддержку вложенных инструкций в основном коде;
- не предупреждать модель о вложенных файлах без отдельной лабораторной задачи;
- не менять формат пользовательского сообщения.

Критерий готовности: тест с `workspace_root` выше текущей рабочей директории
(`cwd`) показывает, что модель получает только корневые правила.

Проверка: создать временное рабочее пространство с корневым и вложенным
`AGENTS.md`, собрать базовые сообщения из вложенной директории и проверить, что
в системном запросе есть только корневой текст.

## Основной уровень

### 1. Сделать диагностику загрузки инструкций машинно-читаемой

Цель: понять, почему загрузчик инструкций не должен возвращать только готовую
строку системного запроса.

Контекст проблемы: готовая строка удобна для отправки модели, но неудобна для
тестов, трассы и CLI-диагностики. Зрелые harness-системы обычно разделяют текст
для модели и метаданные о его происхождении.

Задание: расширьте механизм так, чтобы вместе с текстом корневого `AGENTS.md`
можно было получить диагностику: абсолютный или относительный путь, статус,
исходный размер, добавленный размер и факт обрезания по `PROJECT_DOC_MAX_BYTES`.

Ограничения:

- формат обращения к модели должен остаться совместимым;
- пустой `AGENTS.md` не считать ошибкой;
- диагностика не должна содержать полный текст инструкций;
- не переносить код в `ContextManager` из следующей ветки.

Критерий готовности: тест может проверить не только итоговую строку, но и
причины: «файл отсутствует», «пустой файл пропущен», «файл использован»,
«текст обрезан».

Проверка: создать четыре временных проекта под разные статусы и проверить
машинно-читаемую диагностику без запуска `ask`.

### 2. Добавить CLI-команду для просмотра корневого `AGENTS.md`

Цель: дать человеку понятный способ проверить, какие инструкции будут добавлены
в системный запрос, не вызывая модель и не разбирая трассу вручную.

Контекст проблемы: пользователь может ошибиться корнем рабочего пространства или
положить файл не туда. Команда просмотра должна отвечать на вопрос: «какой
именно `AGENTS.md` увидит harness?».

Задание: добавьте CLI-команду, например `madharness-mini instructions`, которая
без обращения к модели печатает сведения о корневом `AGENTS.md`: путь, статус,
размер файла, размер текста после применения лимита и краткую подсказку, если
файл не найден.

Ограничения:

- команда не должна обращаться к модели;
- не печатать полный текст `AGENTS.md` по умолчанию;
- не читать файлы вне `Config.root`;
- вывод должен быть стабильным для CLI-теста.

Критерий готовности: `madharness-mini instructions` показывает, откуда будут
взяты проектные инструкции и попадут ли они в системный запрос.

Проверка: временный проект с обычным, пустым и отсутствующим корневым
`AGENTS.md`; CLI-тест проверяет статусы и отсутствие полного текста файла.

## Продвинутый уровень

### 1. Спроектировать поддержку вложенных `AGENTS.md`

Цель: превратить потенциально спорное расширение в осознанное архитектурное
решение с понятным контрактом и проверкой.

Контекст проблемы: базовая ветка читает только корневой `AGENTS.md`. Если
добавлять вложенные инструкции, нужно решить, от чего зависит область действия:
от `Config.cwd`, от целевого файла инструмента или от отдельного режима.

Индустриальный ориентир: зрелые harness-системы явно описывают порядок
источников инструкций, область действия и приоритет, а также показывают это в
диагностике.

Задание: спроектируйте и реализуйте поддержку вложенных `AGENTS.md` в одном
выбранном режиме. Минимальный вариант: читать цепочку от `Config.root` до
`Config.cwd` и добавлять тексты в порядке от общего к локальному. В диагностике
нужно показать каждый источник и его статус.

Ограничения:

- сохранить прежнее поведение «только корневой файл» как режим по умолчанию или
  как явно проверяемую совместимость;
- не читать файлы вне рабочего пространства;
- не добавлять глобальные пользовательские правила в ту же задачу;
- не скрывать порядок применения инструкций.

Критерий готовности: поведение вложенных правил описано в документации, покрыто
тестами и видно в диагностике.

Проверка: создать цепочку `AGENTS.md` в корне, `services/` и
`services/payments/`; проверить порядок, пустые пропуски и обрезание последнего
фрагмента.

### 2. Проверять `AGENTS.md`, применимые к целевому файлу

Цель: разобрать ситуацию, когда стартовый системный запрос собран из корня, но
агент работает с файлом глубоко внутри проекта, где могут быть локальные
правила.

Контекст проблемы: файловые инструменты знают путь, с которым работает агент.
Это позволяет сообщить модели о дополнительных инструкциях для конкретного
файла, не меняя системный запрос во время вызова инструмента.

Индустриальный ориентир: инструмент может возвращать не только данные, но и
структурированную подсказку о политике или ограничениях, которые влияют на
дальнейшее решение модели.

Задание: добавьте диагностику для `read_file`, `write_file` и `apply_patch`.
Если для целевого пути есть вложенные `AGENTS.md`, которые не попали в стартовый
системный запрос, ответ инструмента должен перечислить их относительные пути в
поле вроде `applicable_instructions`.

Ограничения:

- не читать полный текст дополнительных инструкций автоматически;
- не менять системный запрос во время вызова инструмента;
- не ломать текущий JSON-ответ инструмента;
- не включать эту диагностику для файлов вне рабочего пространства.

Критерий готовности: модель получает явный сигнал, что для целевого файла есть
дополнительные локальные правила, но базовая загрузка инструкций остаётся
контролируемой.

Проверка: создать проект с корневым `AGENTS.md` и вложенным
`services/payments/AGENTS.md`, вызвать файловый инструмент для
`services/payments/app.py` и проверить ответ инструмента.

## Проверка

Запускайте тесты из корня репозитория:

```bash
uv run -m unittest discover -s tests
```

После выполнения задачи проверьте:

- какой `AGENTS.md` модель фактически получила;
- виден ли источник инструкций в трассе или CLI-диагностике;
- не попал ли полный текст правил или секреты в трассу;
- осталась ли граница рабочего пространства неизменной.
