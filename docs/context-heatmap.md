# Руководство по context_heatmap

`context_heatmap` — пакет пассивной диагностики контекста. Он читает JSONL-трассы
`madharness-mini`, восстанавливает prompt-пакеты перед обращениями к модели и
строит отчёты о том, какие части контекста занимали окно, какие фрагменты
выглядели дорогими или рискованными и где агент действовал без свежего
доказательства в запросе к модели.

Пакет в коде называется `context_heatmap`, а установленная консольная команда —
`context-heatmap`. В документации ниже `context_heatmap` означает Python-пакет,
а `context-heatmap` — CLI-команду.

## Запуск через uv

Анализатор входит в тот же пакет, что и сам harness: точка входа
`context-heatmap` объявлена в `pyproject.toml` рядом с `madharness-mini`.
Поэтому отдельная установка не нужна — из клона репозитория команду запускает
`uv run`, который сам поднимает окружение проекта:

```bash
uv run context-heatmap validate --input .madharness-mini/traces/20260617-120305.jsonl
```

Команды ниже выполняйте из корня репозитория `madharness-mini`: так `uv`
находит `pyproject.toml` и среду проекта. Если команда установлена глобально
через `uv tool install`, префикс `uv run` можно опускать — но в примерах далее
он указан явно, чтобы примеры работали из коробки в любой рабочей копии.

## Когда запускать анализатор

Тепловая карта полезна после реального `ask` или `run`, когда нужно понять не
только итог ответа, но и качество контекстной траектории:

- почему запросы к модели раздулись к концу сессии;
- какие фрагменты занимают большую долю окна;
- не протащились ли старые ответы инструментов, длинная история ассистента или
  дорогие схемы инструментов;
- оставались ли в запросе к модели свежие чтения файлов, тесты и пользовательские
  ограничения перед правками;
- сколько места занимают защищённые слои: системные правила, проектные
  инструкции, активная цель пользователя;
- есть ли предупреждения о старой трассе, неполном `context_packet` или
  проблемной JSONL-структуре.

Важно: анализатор ничего не меняет в поведении агента. Он не сжимает историю, не
переставляет фрагменты, не блокирует инструменты и не исправляет сессию
автоматически. Его задача — показать диагностические признаки, по которым
человек или будущая политика контекста могут принять решение.

## Быстрый сценарий

Сначала получите трассу обычным запуском harness:

```bash
madharness-mini run "Найди команду для запуска тестов и объясни, что она проверяет"
```

После завершения CLI печатает путь вида:

```text
Trace: .madharness-mini/traces/20260617-120305.jsonl
```

Проверьте, что трасса пригодна для анализа:

```bash
uv run context-heatmap validate --input .madharness-mini/traces/20260617-120305.jsonl
```

Нормализуйте события в переносимый формат:

```bash
uv run context-heatmap normalize \
  --input .madharness-mini/traces/20260617-120305.jsonl \
  --out reports/context-heatmap/20260617-120305/normalized
```

Постройте анализ одной сессии:

```bash
uv run context-heatmap analyze \
  --events reports/context-heatmap/20260617-120305/normalized/events.jsonl \
  --out reports/context-heatmap/20260617-120305/session
```

Откройте `reports/context-heatmap/20260617-120305/session/heatmap.html` в
браузере или начните с краткого
`reports/context-heatmap/20260617-120305/session/report.md`.

Если HTML нужно пересобрать после ручной правки машинных файлов отчёта,
используйте отдельную команду:

```bash
uv run context-heatmap render \
  --report reports/context-heatmap/20260617-120305/session/session_report.json \
  --out reports/context-heatmap/20260617-120305/session/heatmap.html
```

Для каталога трасс можно сразу построить отчёты по всем `*.jsonl`:

```bash
uv run context-heatmap analyze-batch \
  --input .madharness-mini/traces \
  --out reports/context-heatmap/corpus
```

`analyze-batch` создаёт отдельный подкаталог на каждую трассу и общий
`corpus_report.jsonl` с краткими итогами сессий.

## Что считается входом

Команда `context-heatmap` принимает трассы `madharness-mini`, которые лежат в
`.madharness-mini/traces`. Внутри это JSONL: одна строка — одно событие
harness.

Для новой трассы главный источник данных — событие `model_call_started` с полем
`context_report.context_packet`. Этот пакет не содержит полный запрос к модели.
Он хранит индекс prompt-сборки:

- `units` — фрагменты prompt-пакета в порядке включения;
- `source_type`, `source_name`, `source_ref` — тип, имя и ссылка на источник;
- `tokens_estimate`, `position_start`, `position_end` — примерный размер и
  позиция фрагмента в запросе;
- `included_because` — почему фрагмент попал в prompt-пакет;
- `content_hash` — hash содержимого без записи полного текста;
- `confidence` — уверенность реконструкции;
- `context_layer`, `authority_level`, `evictability`, `stability`,
  `applicability`, `normative_role`, `goal_role` — классификация слоя контекста.

Старые трассы без `context_packet` тоже читаются, но хуже. Анализатор
восстанавливает фрагменты из обычного `context_report`, помечает сессию
предупреждением `legacy_trace_without_context_packet` и снижает
`reconstruction_confidence`. Такой отчёт годится для грубой диагностики размера
и истории, но не для тонких выводов о позициях и защищённых слоях.

## Команды CLI

### validate

```bash
uv run context-heatmap validate --input .madharness-mini/traces/<trace-id>.jsonl
```

`validate` быстро проверяет, что вход читается и содержит обращения к модели.
Команда печатает:

- общее число событий;
- число обращений к модели;
- число предупреждений (`warnings`);
- число ошибок `context_packet`;
- первые предупреждения и первые ошибки схемы.

Ненулевой код выхода означает, что трасса не подходит для нормального анализа.
Типичные причины:

- файл не JSONL;
- строки JSONL не являются объектами;
- в трассе нет `model_call_started`;
- `context_packet.units` имеет неверную форму;
- позиции фрагментов не монотонны;
- `tokens_estimate` не совпадает с `position_start` и `position_end`;
- у фрагмента нет обязательных полей вроде `content_hash` или `confidence`.

### normalize

```bash
uv run context-heatmap normalize --input <trace-or-dir> --out <normalized-dir>
```

`normalize` переводит исходную трассу в общий формат `SessionEvent`. На выходе
появляются:

- `events.jsonl` — нормализованные события;
- `warnings.jsonl` — предупреждения загрузчика.

`--input` может быть одним JSONL-файлом или каталогом. Если передан каталог,
загрузчик читает все `*.jsonl` внутри и складывает события в один поток. Для
сравнения нескольких сессий обычно удобнее использовать `analyze-batch`, а не
объединять каталог через `normalize`.

### analyze

```bash
uv run context-heatmap analyze --events <normalized-dir>/events.jsonl --out <session-dir>
```

`analyze` читает `events.jsonl`, подхватывает соседний `warnings.jsonl`, если он
есть, восстанавливает prompt-пакеты, считает heat, ищет cold gaps и пишет все
артефакты одной сессии. Команда также автоматически строит `heatmap.html` и
`heatmap.png`.

### render

```bash
uv run context-heatmap render --report <session-dir>/session_report.json --out <session-dir>/heatmap.html
```

`render` пересобирает только HTML по уже готовым файлам отчёта. Команда ожидает,
что рядом с `session_report.json` лежат `turn_heat.jsonl`,
`fragment_heat.jsonl`, `fragments.jsonl`, `packets.jsonl`, `events.jsonl` и
`findings.jsonl`. Если части файлов нет, HTML всё равно соберётся, но
соответствующие вкладки будут беднее.

### analyze-batch

```bash
uv run context-heatmap analyze-batch --input .madharness-mini/traces --out reports/context-heatmap/corpus
```

`analyze-batch` проходит по каждому `*.jsonl` во входном каталоге, создаёт
отдельный отчёт сессии в `<out>/<trace-stem>/` и пишет корпусные сводки:

- `corpus_report.jsonl` — один JSON-объект на сессию;
- `corpus_report.json` — общий итог с максимальными значениями
  `max_red_token_share` и `max_cold_gap_score`.

Эта команда нужна для калибровки: один горячий отчёт может быть случайностью, а
20-50 сессий уже показывают устойчивые проблемы контекстной политики.

## Выходные файлы одной сессии

`analyze` создаёт в каталоге `--out` полный набор файлов.

`session_report.json` — главный машинный итог. В нём лежат идентификатор сессии,
число ходов и обращений к модели, максимальные значения ключевых сигналов,
счётчики находок (`findings`) и предупреждений (`warnings`), первые основные
находки и карта выходных файлов.

`report.md` — короткий текстовый отчёт. Его удобно читать первым в терминале или
в редакторе: там есть краткое состояние, самые горячие обращения и основные
находки.

`heatmap.html` — самодостаточная интерактивная страница. Она хранит данные
внутри HTML и не требует сервера.

`heatmap.png` — компактный обзорный снимок. Это не замена HTML, а быстрая
картинка для сравнения сессий, вставки в заметки или просмотра без
интерактивности.

`events.jsonl` — нормализованные события, из которых строился отчёт.

`fragments.jsonl` — уникальные фрагменты контекста: тип источника, слой,
примерный размер, hash, доверие, taint, целевые пути и безопасные метаданные.

`packets.jsonl` — prompt-пакеты перед каждым обращением к модели. Здесь видно,
какие фрагменты реально были включены, в каком порядке и на каких позициях
окна.

`fragment_heat.jsonl` и `fragment_heat.csv` — оценка каждого фрагмента в каждом
prompt-пакете. Эти файлы нужны, когда надо найти конкретный источник нагрева.

`turn_heat.jsonl` и `turn_heat.csv` — агрегаты по обращению к модели. Эти файлы
удобны для графиков и сортировки ходов по риску.

`findings.jsonl` — человекочитаемые предупреждения с причиной, уверенностью,
ссылками на события и рекомендацией.

`warnings.jsonl` — технические предупреждения загрузки и реконструкции.

## Как читать session_report.json

Начинайте с верхних полей:

- `model_calls` — сколько обращений к модели удалось восстановить;
- `turns` — сколько ходов попало в отчёт;
- `warnings` — сколько технических предупреждений возникло;
- `findings` — сколько диагностических находок найдено.

Затем смотрите максимальные показатели:

- `max_red_token_share` — наибольшая доля токенов, занятая красными
  незашищёнными фрагментами;
- `mean_red_token_share` — средняя красная доля по обращениям к модели;
- `max_cold_gap_score` — худший сигнал действия без свежего доказательства;
- `max_window_pressure_score` — худший сигнал накопления истории ассистента в
  окне (`window_pressure`). Ненулевое значение означает, что доля
  `assistant_message` росла сверх порога без summarization;
- `max_assistant_share` / `mean_assistant_share` — пиковая и средняя доля окна,
  занятая накопленной историей ответов ассистента. Высокий `max_assistant_share`
  при нулевом `red_token_share` — типичный признак слепой зоны heat-модели:
  окно заполнено, но «красных» фрагментов нет;
- `max_fixed_instruction_cost` — максимальная доля окна, занятая нормативным
  слоем: системными и project/developer-инструкциями;
- `max_goal_anchor_cost` — максимальная доля окна, занятая активной целью
  пользователя;
- `max_normative_status` — худшая проблема защищённого нормативного слоя;
- `max_goal_status` — худшая проблема целевого слоя;
- `max_instruction_scope_score` — сильнейший сигнал инструкции не из той области
  применения;
- `max_goal_supersession_score` — сильнейший сигнал устаревшей или вытесненной
  цели;
- `max_attached_data_taint_score` — сильнейший риск вложенных пользовательских
  данных, например блока с внешним текстом.

Хорошее первое правило чтения: если `warnings > 0`, сначала откройте
`warnings.jsonl`; если `findings > 0`, затем откройте `findings.jsonl`; если
`max_red_token_share` или `max_cold_gap_score` велики, переходите в HTML.

## Как читать heatmap.html

HTML состоит из трёх вкладок и боковой панели деталей.

### Fragment Heat

Эта вкладка показывает таблицу «фрагмент × обращение к модели». Ячейка отражает
оценку heat конкретного фрагмента в конкретном prompt-пакете.

Цвета читаются так:

- зелёный — низкий риск;
- жёлтый — фрагмент заметен по стоимости или слабому сигналу;
- оранжевый — фрагмент требует внимания;
- красный — фрагмент сильно нагревает контекст или имеет защищённую проблему;
- серый у защищённого слоя — фиксированная стоимость есть, но проблемы правила
  нет.

Внутри ячейки смотрите не только число heat, но и `reasons`: они объясняют, чем
именно плох фрагмент. Например, `large_or_repeated_fragment` указывает на
крупный или повторяющийся фрагмент, `duplicate_context` — на повтор hash,
`middle_position` — на риск неудобной позиции в заполненном окне,
`tainted_or_untrusted` — на недоверенный или секретный материал.

### Context Window

Эта вкладка показывает каждое обращение к модели как вертикальный столбец
контекстного окна. Верх столбца — начало prompt-пакета, низ — предел окна. Цветные
сегменты внутри столбца соответствуют типам источников:

- `system_instruction` — системные инструкции;
- `developer_instruction` — developer/project-инструкции и похожий нормативный
  слой;
- `user_message` — активная цель пользователя и вложенные пользовательские
  данные;
- `context_fragment` — обычные фрагменты контекста;
- `file_snippet` — чтения файлов;
- `test_result` — результаты тестов;
- `tool_schema` — схемы доступных инструментов;
- `assistant_message` — история ответов ассистента;
- `tool_output` — сырые ответы инструментов;
- `unknown` — всё, что анализатор не смог классифицировать точнее.

Белая часть столбца — неиспользованная доля окна. Если её почти нет, сессия
близка к бюджетному пределу. Если окно заполнено в основном `assistant_message`
и `tool_output`, проблема обычно в накопленной истории и сырых наблюдениях. Если
много `tool_schema`, проверьте, не выдано ли модели слишком много инструментов.
Если значительную часть стабильно занимают `system_instruction` и
`developer_instruction`, это фиксированная цена правил, а не обязательно ошибка.

Клик по сегменту открывает справа безопасные метаданные: `fragment_id`,
`source_type`, `source_name`, слой, `authority_level`, размер, причины heat и
связанные пути. Полный текст запроса и длинные ответы инструментов в HTML не
раскрываются.

### Findings

Вкладка Findings показывает предупреждения, которые уже сформулированы для
человека. Анализатор ищет cold gaps — действия без свежего доказательства в
окне. Все такие находки имеют `kind="cold_gap"` и различаются `title` и
`explanation`, а их `cold_gap_score` агрегируется в `max_cold_gap_score`
сессии.

Сейчас ловятся четыре класса холодных дыр:

1. **Правка файла без актуального чтения** (`confidence=0.72`) — повторная
   правка того же пути без `read_file` между правками. Классический сценарий:
   файл уже существует или уже правился, а свежего чтения перед новой правкой
   нет. Первичное создание файла сюда не относится: читать ещё нечего.
2. **Правка при отсутствии спецификации в окне** (`confidence=0.72`) — правка,
   когда ключевой документ задачи (ТЗ, контракт) отсутствует в текущем
   prompt-пакете. Документ-спецификацию анализатор выявляет по размеру: крупное
   чтение до первой правки. Эта сигнатура ловит потерю source-of-truth после
   summarization: ТЗ сворачивается в дайджест-указатель, а модель продолжает
   писать код по тающей памяти о задаче.
3. **Правка после сворачивания чтения summarization'ом** (`confidence=0.70`)
   — правка сразу после хода, где summarization свернул `read_file` критического
   документа. Это холодная дыра от возрастной эвикции: harness заменяет
   содержимое файла указателем «content read earlier», но модель не
   перечитывает путь и действует без свежего состояния.

   В такой finding стоит входить внимательно: после исправлений harness он может
   оказаться как реальной холодной дырой, так и артефактом телеметрии. Различайте:
   - **Реальный fan-out**. Модель читает контракт (интерфейс, ТЗ) и затем правит
     много зависимых файлов. Если harness свернул контракт, а правки шли по другим
     путям, модель действительно теряет источник правды. Защиту такого сценария
     управляют параметры `context_contract_protection_turns` и
     `context_contract_protection_writes`: при ≥ N правок других путей за K ходов
     после чтения контракт удерживается в окне. Если finding остаётся — пороги
     слишком малы для вашей задачи, поднимите K или N.
   - **Артефакт телеметрии**. Если `context_packet.units` для свёрнутого чтения не
     содержит `metadata.tool_name == "read_file"` или `metadata.path`, анализатор
     не может восстановить, что это было именно чтение, и ставит ложный cold gap.
     Современный harness проставляет эти поля как для свежих, так и для
     свёрнутых (digest) наблюдений; их отсутствие означает устаревшую трассу.
4. **Аномальная частота повторных чтений файла** (`confidence=0.55`,
   `severity=low`) — путь перечитан ≥3 раз за последние 6 ходов. Это не
   классический cold gap, а компенсаторное поведение при потере доверия к
   контексту: summarization ломает память, и модель постоянно перечитывает
   файлы заново.
5. **Цикл неудачных правок файла** (`confidence=0.60`, `severity=low`) —
   `apply_patch` по пути завершился ошибкой ≥2 раз за последние 8 ходов.
   Симптом рассинхронизации: модель генерирует патч по устаревшему
   воспоминанию о файле, а harness применяет его к актуальному содержимому,
   что даёт `expected 1 hunk match, found 0`. Каждый такой оборот — отдельное
   обращение к модели, поэтому цикл дороже read storm по токенам. Успешная
   правка путь сбрасывает счётчик.

Если на одну и ту же правку (`event_id` + путь) реагируют сразу несколько
сигнатур, анализатор оставляет одну находку с наибольшим `cold_gap_score`.

Отдельный класс находок — `window_pressure` (`kind="window_pressure"`). Это не
холодная дыра, а сигнал накопления истории ответов ассистента в окне без
summarization/компрессии. `red_token_share` здесь слеп: отдельные
`assistant_message`-фрагменты намеренно низкого heat, поэтому общую долю
ассистента в окне (`assistant_share`) анализатор считает отдельно и ловит рост.

6. **Накопление истории ассистента в окне** (`confidence=0.70`,
   `severity=medium`) — доля `assistant_message` превысила порог 0.40 и
   продолжает расти к предыдущему обращению к модели (прирост ≥ 0.02). Plateau
   (стабильно занятое окно без роста) НЕ сигналит — важен именно рост без
   свёртки. Симптом: summarization сворачивает только tool-обороты, а
   ассистентские сообщения копятся дословно и вытесняют доказательства.

Для каждого finding смотрите:

- `severity` — критичность;
- `kind` — тип находки;
- `turn_id` — ход, где возник риск;
- `explanation` — почему анализатор считает это проблемой;
- `recommendation` — что сделать в следующем запуске или в политике контекста;
- `event_ids` — события трассы, на которых основан вывод;
- `confidence` и `scores` — насколько уверенно выставлен сигнал.

## Как читать heatmap.png

`heatmap.png` нужен для быстрого обзора, когда открывать HTML неудобно.

Верхняя строка показывает `session_id`, число обращений к модели, максимальную
заполненность окна, максимальные стоимости `FIX` и `GOAL`, protected-статусы,
максимальный `COLD`, максимальную долю ассистента `ASST` и число `FINDINGS`.
Здесь `GOAL` в заголовке — стоимость удержания активной цели, а не нижняя
строка `GOAL` в блоке `TURN SIGNALS`.

Центральный график читается слева направо. Каждый узкий столбец — одно
обращение к модели. Цветные участки показывают, какие типы источников занимали
окно, а белая область показывает свободную часть. Чем меньше белого, тем выше
давление на бюджет.

Нижние мини-графики показывают агрегированные сигналы по тем же обращениям:

- `TOOL` — доля сырых ответов инструментов;
- `ASST` — доля накопленной истории ответов ассистента (`assistant_share`);
  резкий рост этой полосы — симптом `window_pressure`;
- `EVID` — плотность доказательств;
- `POS` — позиционная пригодность доказательств;
- `NORM` — худший protected-сигнал нормативного слоя;
- `GOAL` — худший protected-сигнал целевого слоя;
- `COLD` — cold gaps;
- красные и оранжевые маркеры — бюджетное давление и красная доля токенов.

Если PNG показывает всплеск `COLD`, переходите в `findings.jsonl` и HTML. Если
виден резкий рост заполненности окна, смотрите `packets.jsonl` и вкладку
Context Window. Если заметна большая красная доля, открывайте
`fragment_heat.jsonl` или вкладку Fragment Heat.

## Основные метрики turn_heat

`turn_heat.jsonl` описывает одно обращение к модели одной строкой.

`red_token_share` — доля токенов, занятая красными незашищёнными фрагментами.
Защищённые фрагменты правил и цели исключаются из этой доли, пока у них нет
собственной проблемы protected-слоя.

`stale_token_share` — доля токенов с признаками устаревания.

`raw_tool_share` — доля окна, занятая сырыми ответами инструментов.

`assistant_share` — доля окна, занятая накопленной историей ответов ассистента.
Этот сигнал введён отдельно, потому что `red_token_share` здесь слеп: отдельные
`assistant_message`-фрагменты намеренно низкого heat (опасна не одна мессага, а
их сумма). Если `assistant_share` стабильно растёт и переваливает за ~0.40,
смотрите находку `window_pressure` и проверяйте политику summarization —
история копится без свёртки и вытесняет доказательства.

`evidence_density` — доля окна, занятая доказательствами: пользовательским
сообщением, чтениями файлов, результатами тестов и ответами инструментов.

`cold_gap_score` — сила сигнала, что перед действием не хватало свежего
доказательства. Складывается из пяти классов находок (см. раздел Findings):
правка без актуального чтения, правка без спецификации в окне, правка после
сворачивания чтения summarization'ом, аномальная частота перечитываний и цикл
неудачных правок файла. На ход берётся максимум `cold_gap_score` по всем
холодным дырам в нём.

`window_pressure_score` — сила сигнала `window_pressure` на этом ходе:
накопление истории ответов ассистента в окне без summarization/компрессии. На
ход берётся максимум `window_pressure_score` по находкам этого класса. 0
означает, что роста доли `assistant_message` сверх порога не зафиксировано.

`positioned_evidence_score` — насколько удачно расположены доказательства.
Низкое значение означает, что важные фрагменты могли оказаться в середине
переполненного запроса, где их легче потерять.

`growth_slope` — насколько быстро вырос запрос относительно предыдущего
обращения к модели.

`taint_exposure` — доля окна, связанная с недоверенным, потенциально
инъекционным или секретным материалом.

`fixed_instruction_cost` — доля нормативного слоя. Это цена правил, а не
автоматическая ошибка.

`goal_anchor_cost` — доля активной цели пользователя. Это цена удержания задачи,
а не автоматическая ошибка.

`normative_status` — худший protected-сигнал для правил: конфликт,
устаревание, дублирование, неверная область применения, нарушение целостности
или taint.

`goal_status` — худший protected-сигнал для цели: потеря критериев, вытеснение
новой целью, конфликт, зависшая завершённая цель, cold gap или taint вложенных
данных.

`top_reasons` — самые частые причины heat в этом обращении к модели.

## Основные поля fragment_heat

`fragment_heat.jsonl` помогает перейти от общего риска к конкретному фрагменту.

`heat` — итоговая оценка от 0 до 1. Для обычных фрагментов она складывается из
давления на окно, риска и влияния. Для защищённых слоёв это не цена длины, а
наличие проблемы правила или цели.

`ordinary_cost` — обычная стоимость фрагмента по старой heat-логике. У
защищённых слоёв она сохраняется отдельно, чтобы видеть, сколько места занимают
правила и цель.

`protected_status` — проблема защищённого слоя. Ноль означает, что дорогой
нормативный фрагмент просто занимает фиксированное место; высокое значение
означает конфликт, устаревание, неверную область применения, taint или похожий
риск.

`excluded_from_red_token_share` — признак, что защищённый фрагмент не увеличивает
`red_token_share`, потому что его `protected_status` ниже красного порога.

`axes` — подробные оси оценки. Для обычного фрагмента важны `pressure`,
`low_utility`, `staleness`, `duplication`, `position_risk`, `taint`,
`compression_risk`. Для защищённых слоёв добавляются
`instruction_*`, `goal_*` и `attached_data_taint_score`.

`reasons` — стабильные строковые причины для человека и тестов. Они удобнее для
быстрой фильтрации, чем числовые оси.

`confidence` — уверенность анализа. У legacy-трасс и восстановленных данных она
ниже.

`evidence_event_ids` — события, из которых был получен фрагмент.

## Защищённые слои: почему правила не всегда красные

Системные инструкции, project/developer-инструкции и активная цель пользователя
часто занимают много места. Простая heat-модель могла бы красить их в красный
только из-за размера, но это было бы неверно: такие фрагменты нельзя просто
выкинуть ради экономии.

Поэтому `context_heatmap` разводит два вопроса:

- сколько места занимает защищённый фрагмент;
- есть ли у защищённого фрагмента собственная проблема.

Размер отражается в `ordinary_cost`, `fixed_instruction_cost` и
`goal_anchor_cost`. Проблемы отражаются в `protected_status`,
`normative_status` и `goal_status`.

Для нормативного слоя проблемными причинами считаются:

- `instruction_conflict` — конфликт правил;
- `instruction_stale_or_superseded` — устаревшая или вытесненная инструкция;
- `instruction_duplicate` — дублирование одного и того же правила;
- `instruction_scope_mismatch` — правило не из той области применения;
- `instruction_integrity_problem` — подозрительный `authority_level` или
  отсутствие целостного hash;
- `instruction_tainted_or_untrusted` — недоверенный нормативный материал.

Для целевого слоя проблемными причинами считаются:

- `goal_integrity_loss` — потеря важных критериев задачи;
- `goal_superseded` — цель вытеснена новой;
- `goal_conflict` — конфликт целей;
- `goal_overhang` — завершённая или неактивная цель продолжает занимать окно;
- `goal_cold_gap` — цель требует доказательства, которого не оказалось рядом;
- `attached_data_taint` — вложенные пользовательские данные выглядят
  недоверенными.

Практический вывод: большой `fixed_instruction_cost` сам по себе не требует
удалять правила. Но большой `fixed_instruction_cost` вместе с высоким
`normative_status` уже говорит, что нужно искать конфликт, дубликат или
неактуальную инструкцию.

## Как расследовать типичные проблемы

Если запросы стали слишком большими, отсортируйте `turn_heat.csv` по
`red_token_share`, затем откройте соответствующий `model_call_id` в HTML. В
Context Window посмотрите, какой `source_type` занимает большую часть окна. Если
это `assistant_message`, проблема в длинной истории; если `tool_output` — в
сырых наблюдениях; если `tool_schema` — в слишком широком наборе инструментов.

Если анализатор нашёл cold gap, начните с `findings.jsonl`. Найдите `event_ids`,
сверьте их с `events.jsonl`, затем проверьте, был ли перед правкой актуальный
`read_file`, `list_files` или другой источник знания о текущем состоянии. Для
следующего запуска исправление обычно простое: перечитать файл перед patch или
сохранить в трассе доказательство, что состояние уже известно.

Если много `legacy_trace_without_context_packet`, переснимите трассу новой
версией harness. Legacy-режим помогает увидеть грубую картину, но не даёт
полного качества по позициям, слоям и protected-сигналам.

Если высокая доля `raw_tool_share`, проверьте, не попадают ли в историю длинные
логи, полные JSON-ответы или повторные выводы команд. Для будущей политики это
кандидаты на краткую сводку, обрезку или повторное чтение только нужного
фрагмента.

Если высокий `taint_exposure`, найдите фрагменты с причиной
`tainted_or_untrusted` или `attached_data_taint`. Особенно внимательно смотрите
внешний текст, пользовательские вложения и ответы инструментов, которые могут
содержать инструкции без нужного `authority_level`.

Если высокий `goal_status`, проверьте активную цель пользователя. Часто это
означает, что в запросе к модели осталась старая цель, потерялись критерии
готовности или вложенный блок пользовательского текста был ошибочно воспринят
как часть главной задачи.

Если высокий `fixed_instruction_cost`, сначала проверьте, это стабильная цена
правил или настоящая проблема. При низком `normative_status` это просто большой
нормативный слой. При высоком `normative_status` ищите дубли, конфликтующие
инструкции, неверную область применения или недоверенный источник правил.

## Пороговые значения для первого чтения

Точные пороги нужно калибровать на корпусе сессий, но для ручного разбора можно
использовать такие ориентиры:

- `red_token_share < 0.10` — обычно спокойно;
- `red_token_share` от `0.10` до `0.25` — стоит посмотреть горячие фрагменты;
- `red_token_share > 0.25` — вероятно, контекст заметно загрязнён;
- `cold_gap_score >= 0.50` — нужно проверить находки;
- `assistant_share` от `0.40` с ростом — накопление истории ассистента, смотрите
  находку `window_pressure` и проверяйте политику summarization; стабильная
  доля без роста не сигналит;
- `raw_tool_share > 0.30` — возможно, в запросе слишком много сырого вывода;
- `taint_exposure > 0.10` — стоит проверить недоверенные источники;
- `normative_status >= 0.50` — есть проблема в защищённых инструкциях;
- `goal_status >= 0.50` — есть проблема в активной цели или вложенных данных.

Эти числа не являются политикой блокировки. Они помогают выбрать, куда смотреть
первым.

## Безопасность и приватность

`context_packet` и отчёты построены как индекс, а не как копия запроса к модели.
В них не должны попадать полный запрос, длинные ответы инструментов и секреты.
Анализатор использует hash, размеры, метаданные источников и замаскированные
выдержки для диагностики.

Тем не менее отчёты остаются диагностическими артефактами проекта. Они могут
содержать имена файлов, имена инструментов, размеры фрагментов, краткие
замаскированные выдержки из observation и сведения о пользовательской задаче. Не
публикуйте каталог отчётов как полностью обезличенный лог без отдельной
проверки.

## Ограничения MVP

Тепловая карта показывает подозрительные участки, но не доказывает причинность.
Если после горячего обращения к модели агент ошибся, heat объясняет возможные
причины, но не заменяет повторный прогон, ручное чтение трассы и сравнение с
контрольными запусками.

Оценка токенов основана на приближении `char_estimate`, поэтому абсолютные числа
не надо читать как точный токенизатор конкретной модели. Важнее относительные
доли, рост по ходу сессии и повторяемость паттерна на корпусе.

Legacy-трассы имеют сниженную уверенность. Чем меньше `context_packet`, тем
осторожнее надо читать позиционный риск, защищённые слои и причины heat.

Cold gap в MVP ищет только часть ситуаций: прежде всего правки файлов без
актуального чтения. Отсутствие находки не означает, что все доказательства были
идеально сохранены.

## Минимальный чеклист разбора

1. Запустите `validate`.
2. Если есть предупреждения, прочитайте `warnings.jsonl`.
3. Откройте `report.md` и `session_report.json`.
4. Если есть находки, прочитайте `findings.jsonl`.
5. В HTML откройте Context Window и найдите самое заполненное обращение к модели.
6. В Fragment Heat откройте самые красные или оранжевые ячейки.
7. В `turn_heat.csv` отсортируйте строки по `red_token_share`,
   `cold_gap_score`, `raw_tool_share` и `taint_exposure`.
8. Сформулируйте причину: история, сырой ответ инструмента, схемы, правила, цель,
   taint, legacy-реконструкция или cold gap.
9. Только после этого решайте, нужна ли политика: сводка, перечитывание файла,
   уменьшение набора инструментов, разделение вложенных пользовательских данных,
   пересъём трассы или правка инструкций.
