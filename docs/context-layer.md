# Слой контекста

Слой контекста отвечает за то, какие сообщения модель видит в `ask` и `run`.
Он живёт в пакете `madharness_mini.context` и не зависит от конфига, политики
безопасности, клиента модели или обработчиков инструментов. Внешний код
передаёт ему готовые тексты и события, а на выходе получает список `messages` для
OpenAI-совместимого Chat Completions API.

`messages` — это ровно тот список сообщений, который харнесс отправляет в поле
`messages` HTTP-запроса к модели: системные правила, задача пользователя,
ответы assistant и результаты инструментов.

## Основные типы

`ContextFragment` описывает отдельный кусок контекста: системный запрос,
проектные инструкции, подсказку навыка или MCP-фрагмент. У фрагмента есть
`id`, `source`, `text`, `priority`, `placement` и `transient`.

`ContextProvider` — простой протокол расширения. Провайдер получает
`ContextState` и возвращает дополнительные `ContextFragment`. В полной версии
так подключается каталог Agent Skills без импорта `loop.py` или `model.py`.

`ContextManager` хранит задачу пользователя, закреплённые фрагменты и историю
assistant/tool сообщений. Основной метод `messages()` возвращает готовый список
сообщений для модели, а `stats()` показывает примерную токеновую оценку
собранного контекста и факт обрезки.

`report()` возвращает более подробный отчёт о контексте для трасс и отладки. Он
показывает токеновую оценку до и после бюджетной обработки, список фрагментов с
их источниками и размерами, количество элементов истории, обрезанные
tool-сообщения и удалённые старые элементы истории. Сам текст запроса и вывод
инструментов в отчёт не попадает, чтобы трасса оставалась компактной и не
дублировала чувствительный контент.

## Как используется в `run`

`context/bootstrap.py` создаёт `ContextManager` через `base_context()`, читает
встроенный промпт и `AGENTS.md`, затем добавляет их как закреплённый
`ContextFragment`. `loop.py` использует эту сборку как часть `ask` и `run`.

Закреплённый фрагмент — это часть контекста, которую нельзя удалить при обрезке
старой истории. Например, системный промпт и правила проекта должны оставаться
видимыми модели даже тогда, когда результаты старых инструментов уже не влезают
в бюджет контекста.

После каждого ответа модели `model_loop.py` вызывает `record_assistant()`. Если
модель запросила инструмент, результат записывается через `record_tool_result()`.
Сообщение assistant с `tool_calls` и соответствующие `role=tool` ответы хранятся
как атомарный элемент истории: при обрезке они сохраняются или удаляются вместе.

Перед сохранением assistant-сообщение нормализуется: в историю попадают только
поля, которые нужны следующему Chat Completions запросу (`role`, `content`,
`tool_calls`). Специфичные для провайдера поля вроде `reasoning`,
`reasoning_details`, `refusal` и другие диагностические блоки не отправляются
модели повторно.
Длинный assistant `content` укорачивается с пометкой `context clipped`, чтобы
модель не платила за собственные длинные рассуждения на каждом следующем ходе.

Мультимодальные дополнительные сообщения, например вложение из `read_image`,
добавляются после закрытия всех `tool_calls`. Observation инструмента остаётся
текстовым JSON без base64, поэтому трасса не раздувается изображениями.

## Бюджет контекста

Харнесс задаёт бюджет контекста в токенах через `context_max_tokens`, но не
использует tokenizer конкретной модели. OpenAI-совместимый API может вести к
разным провайдерам и моделям, поэтому слой контекста считает консервативную
оценку: сериализует отправляемые данные в компактный JSON, смотрит размер UTF-8
в байтах и делит его на фиксированную цену токена.

Эта оценка не совпадает с точным счётчиком провайдера, зато работает одинаково
для разных моделей и не требует зависимостей времени выполнения. В режиме `run`
в бюджет входят не только `messages`, но и схемы доступных `tools`, потому что
они тоже отправляются модели при каждом вызове.

Настройки:

| Поле | Значение по умолчанию | Смысл |
| --- | --- | --- |
| `context_max_tokens` | `60000` | Примерный максимум токенов запроса к модели. |
| `context_keep_recent_turns` | `3` | Сколько последних элементов истории сохранять при удалении старых. |
| `context_reserve_tokens` | `0` (выкл) | Headroom: дроп истории срабатывает при оценке свыше `max_tokens − reserve`, оставляя запас. `0` — прежнее поведение (дроп у самого `max_tokens`). |

Закреплённые фрагменты и исходная задача пользователя не удаляются. Если контекст
слишком большой, сначала укорачивается вывод `role=tool` с явной пометкой
`context clipped`. Если этого мало, старые неприкреплённые элементы истории
удаляются целиком.

`context_keep_recent_turns` — это предпочтение, а не разрешение превысить бюджет.
Если сохранённые недавние элементы всё ещё не помещаются, `ContextManager`
принудительно удаляет и их. Если и forced-drop не помогает, включается последний
эшелон recovery: убираются эвиктируемые рабочие фрагменты, затем клипаются
project-инструкции и, в крайнем случае, системный промпт. Это спасает сессию от
падения на пиковом ходе. Только если даже `system + task` не лезут в окно,
поднимается понятная ошибка `context budget exceeded after truncation` — это
действительно fatal (бюджет слишком мал для ядра запроса).

Оценка токенов калибруется по реальному `usage.prompt_tokens` из ответа модели:
коэффициент `_token_ratio` сглаживает разницу между эвристикой `bytes/3` и
настоящим tokenizer провайдера, так что пороги срабатывают точнее. До первого
ответа модели ratio равен 1.0 (поведение прежнее).

После каждой сборки `ContextManager.report()` можно посмотреть, какие именно
бюджетные действия произошли. В режиме `ask` и `run` этот отчёт записывается в
событие трассы `model_call_started` под ключом `context_report`. Отчёт показывает
`messages_tokens_estimate`, `tools_tokens_estimate`, общий
`request_tokens_estimate` и `max_tokens`, чтобы было видно, сколько бюджета
заняли история, системные фрагменты и описания инструментов.

Для тепловой карты контекста отчёт дополнительно содержит
`context_packet`: диагностический индекс prompt-сборки. Он перечисляет
фрагменты, историю и схемы tools в порядке включения, показывает примерные
позиции и размеры, причину включения, hash содержимого и confidence. Полный
текст prompt и длинные tool outputs в `context_packet` не пишутся: trace остаётся
компактной, а анализатор получает достаточно данных для пассивной диагностики.

## Расширение инструментов и контекста

Инструменты расширяются через `ToolProvider`, а контекст — через
`ContextProvider`. Для навыка или MCP-сервера это означает две независимые
точки подключения:

- `ToolProvider.specs(ctx)` отдаёт `ToolSpec` для вызова модели.
- `ContextProvider.collect(state)` отдаёт инструкции или другие фрагменты,
  которые модель должна видеть перед вызовом инструмента.

Так инструмент может появиться без правки агентского цикла, а контекстные
инструкции не смешиваются с кодом выполнения обработчиков.
